# ADR-0001 — Запись разговоров и расшифровка в текст

- **Статус:** Предложено 25.11.2026
- **Контекст:** по итогам звонка нужна запись голоса и текст «кто что сказал». Распознавание — тем же стеком, что в платформе ([platform ADR-0041](../../../platform/docs/adr/0041-voice-input.md), приложение `platform-apps/apps/whisper`): свой faster-whisper, звук не уходит с сервера.

## Решения в двух словах

| Вопрос | Решение сейчас | Потом |
|---|---|---|
| Где распознаём | отдельный контейнер speaches рядом с Vocala | встроить в платформу (тот же API — меняется только адрес) |
| Кто включает запись | любой участник звонка | права |
| Что пишем | только голос, дорожка на участника, без сведения | общий файл, видео |
| Хранение | локально или S3, 30 дней | — |
| Кто видит записи | все участники канала | права |

## 1. Запись — на сервере, дорожка на участника

SFU и так получает звук каждого участника отдельным RTP-потоком (`forwardRTP`, `internal/webrtc/sfu.go`). Пока в канале идёт запись, тот же цикл пишет пакеты аудио в Ogg/Opus через `pion/webrtc/v4/pkg/media/oggwriter`:

- **без перекодирования** — копирование пакетов, процессор не тратится;
- **говорящий известен точно** — у каждого свой файл, диаризация не нужна;
- **без ffmpeg** — сведение в один файл не делаем (решение «проще и производительнее»).

Каждый файл — **сегмент**: от появления дорожки участника до её конца. Переподключение, перезаход, ICE restart с новой дорожкой — новый сегмент. Для сегмента храним время начала по часам сервера; по нему расшифровка раскладывается на общую шкалу времени.

Ogg-писатель pion считает время по записанным сэмплам, а не по RTP-меткам, поэтому:

- потерянные пакеты (пропуск короче секунды) заполняются кадрами тишины — иначе файл короче звонка и всё после потери сдвигается;
- пауза дольше секунды или скачок RTP-меток назад (сброс у клиента) — новый сегмент со своим временем начала.

**Путь пересылки звука не ждёт ни диска, ни базы.** SFU копирует пакет в очередь записи (4096 пакетов) и идёт дальше; файлы пишет отдельная горутина на каждую запись. Переполненная очередь теряет пакеты записи, а не задерживает звонок; число потерь пишется в лог.

**Запасной путь через WebSocket.** Android, как и все, звонит через WebRTC и записывается этим путём. Но если при входе в звонок микрофон получить не удалось, а потом его включили кнопкой (`toggleMute` при `USE_WS_MEDIA`), звук идёт кусками MediaRecorder (WebM/Opus, по 60 мс) по WebSocket (`handleBinaryMedia`, `internal/signaling/hub.go`). Эти куски дописываются в сегмент `.webm` как есть, без перекодирования (MP4 — так же).

У сырого WebM из MediaRecorder нет длительности и индекса (Cues): в браузерном проигрывателе такие дорожки показывают неизвестную длину и плохо перематываются; `duration_ms` в списке верная (по времени прихода кусков). Safari на iOS WebM/Opus воспроизводит плохо. Если станет важно — перепаковка после записи.

Заголовок контейнера есть только в первом куске потока, а без него остальные не прочитать. Поэтому:

- при старте записи сервер шлёт таким клиентам `ws_media_restart`, клиент перезапускает MediaRecorder (новый — только после `onstop` старого);
- перед каждым новым потоком клиент шлёт `ws_media_stream` с MIME-типом, а куски — строго по очереди (цепочка промисов вокруг `Blob.arrayBuffer()`). Сообщения одного WebSocket приходят по порядку, поэтому сервер точно знает, с какого куска начинается поток, и открывает новый сегмент. Искать заголовок по байтам нельзя: Chrome режет его между кусками (первый кусок нового потока бывает в один байт `1a`);
- куски потока, начавшегося до записи (нет `ws_media_stream`), отбрасываются; старый клиент без этих сообщений не записывается, в лог — сколько кусков отброшено;
- время начала сегмента — приход первого куска минус 60 мс, длительность — по времени прихода последнего.

### Включение и выключение

- Кнопка «Запись» у любого участника звонка; остановить может любой.
- Запись останавливается сама, когда из звонка ушёл последний участник, и по пределу длительности (`recording.max_hours`, по умолчанию 4) — чтобы забытая запись не писала сутками.
- Сервер рассылает всем в канале `recording_state`; у всех, включая гостей, — красный индикатор «Идёт запись». Вошедший во время записи видит предупреждение при входе.
- Одна активная запись на канал; запустить новую можно не чаще раза в 2 секунды.
- Остановка сразу сообщается всем, файлы дописываются в фоне. В сообщении об остановке есть `recording_id`: клиент не гасит индикатор новой записи из-за запоздавшей остановки старой.
- Запись без звука (никто не говорил) удаляется при остановке.

## 2. Хранилище — интерфейс с первого дня

```go
// internal/storage
type Blobs interface {
    PutFile(ctx context.Context, key, localPath string) error // переносит готовый файл
    Open(ctx context.Context, key string) (io.ReadCloser, error)
    Delete(ctx context.Context, key string) error
}
```

- `local`: каталог `storage.local.dir`, по умолчанию `storage` рядом с файлом базы (`/var/lib/vocala/storage` в пакетах, том данных в Docker). Ошибка настройки хранилища не мешает серверу стартовать: запись выключается с ошибкой в логе.
- `s3`: тот же интерфейс, настройки `storage.s3.*` (endpoint, bucket, prefix, ключи — лучше через `VOCALA_S3_*`). Клиент — minio-go: работает с любым S3-совместимым хранилищем. Бакет проверяется при старте (не дольше 10 секунд: сервер ждёт этого, прежде чем принимать звонки); `https://`/`http://` в endpoint понимается. Префикс по умолчанию — `vocala/`. `Open` отдаёт объект minio-go, который сам делает `io.ReadSeeker` из запросов с Range, поэтому `http.ServeContent` и перемотка в плеере работают как с локальным файлом. Код записи и расшифровки о бэкенде не знает. Смена бэкенда старые файлы не переносит.
- Пока идёт запись, сегмент пишется во **временный локальный файл** (в S3 нельзя дописывать потоком). По закрытию сегмента — `PutFile` в хранилище и удаление временного. Для `local` это переименование.
- **Сбой хранилища во время работы.** Выгрузка сегмента повторяется 5 раз с паузой от 10 секунд, удваивая её (около 2,5 минут); каждый вызов хранилища ограничен 5 минутами. Не вышло — запись получает `failed`, файл остаётся на диске, а фоновая задача раз в 10 минут (и при старте) догружает такие сегменты; когда все на месте — запись становится `ready` и уходит на расшифровку. Восстановление после падения удаляет строку сегмента только если его нет ни на диске, ни в хранилище (`ErrNotFound`); при любой другой ошибке хранилища строка остаётся до следующей попытки. Какие записи прервались, решается до приёма звонков, а выгрузка их файлов идёт в фоне.
- В базе — **ключи**, не пути: `recordings/{recording_id}/{segment_id}.ogg`, `recordings/{recording_id}/transcript.md`.

## 3. Данные

```
recordings          id, channel_id, started_by_id, started_by_name, started_at_ms,
                    ended_at_ms, status (recording|ready|failed),
                    transcript_status ('' |pending|running|ready|failed),
                    transcript_key, transcript_attempts
recording_segments  id, recording_id, user_id, display_name, started_at_ms,
                    duration_ms, storage_key, format (ogg|webm|mp4), stored
```

`display_name` пишется в сегмент сразу: гостевые сессии временные, через месяц имени гостя уже не найти.

**Срок хранения** — `recording.retention_days: 30`, по образцу `database.chat_retention_days`: фоновая чистка удаляет файлы из хранилища, затем строки. `0` — хранить всегда.

## 4. Расшифровка — после звонка, очередь на одно место

Контейнер speaches с теми же закреплёнными образом (digest как в `platform-apps/apps/whisper/app.yaml`) и настройками: `faster-whisper-medium`, `int8`, CPU, 4 потока, `WHISPER__TTL=-1`, без UI, `cpus: 4`, `mem_limit: 4g`. В `docker-compose.yaml` — сервис `whisper` в профиле `stt` (`docker compose --profile stt up -d` и `VOCALA_STT_URL=http://whisper:8000` в `.env`), без опубликованного порта, в отдельной сети `speech` только с `vocala`; модели — в томе `whisper-models`. В deb-пакет не входит: `transcription.url` пуст — запись работает, расшифровки нет.

Клиент — порт `backend/internal/speech` из платформы (`Prepare` готовит модель при старте, `Clean` вырезает «Продолжение следует», «Субтитры сделал…» и т. п.).

Порядок:

1. Файлы записи в хранилище (после остановки или восстановления после падения) → `recordings.transcript_status = pending`. Очередь — это колонки строки записи (`transcript_status`, `transcript_key`, `transcript_attempts`), а не отдельная таблица: у записи ровно одна расшифровка, и удаление записи по сроку хранения забирает её файл. Переживает перезапуск: задачи в состоянии `running` при старте возвращаются в `pending`.
2. Один фоновый обработчик на сервер, сегменты по одному: `POST /v1/audio/transcriptions` с `language=ru`, `response_format=verbose_json`, `timestamp_granularities[]=segment`, `vad_filter=true`.
3. Фразы из ответа (`segments[].start/end`, секунды) сдвигаются на начало сегмента, всё сортируется по времени и склеивается в `transcript.md`:
   ```
   [00:01:23] Иван: …
   [00:01:31] Мария: …
   ```
   Соседние фразы одного человека с паузой меньше 2 секунд склеиваются в одну строку.
4. `transcript.md` → хранилище (`recordings/<id>/transcript.md`), `transcript_status=ready`, в чат канала — системное сообщение «📝 Transcript of the recording from 15:04 is ready — see Recordings».

Проверено по исходникам speaches 0.8.3 (`routers/stt.py`, `api_types.py`, `config.py`): `verbose_json` возвращает сегменты со `start`/`end`; `timestamp_granularities[]` принимается; `vad_filter` по умолчанию включён; ogg/webm декодирует PyAV. Ограничения размера в коде нет — час opus (≈15 МБ) уходит одним запросом.

**Тайм-аут** — не фиксированные 3 минуты, как в платформе, а от длины сегмента: `5 мин + 2 × длительность`. Ошибка сервиса (4xx/5xx, обрыв соединения посреди запроса — например, сервис упал на длинном файле) — до 3 попыток с паузой в минуту, затем `failed` и кнопка «Try again» в списке записей. Попыткой не считается только то, что до сервиса не дошло: не удалось подключиться (не поднялся, перезапускается, имя не резолвится), 502/503 и 404 «модель не установлена» — задача ждёт 30 секунд и возвращается в очередь. Очередь берёт сначала задачи с меньшим числом попыток, чтобы падающая запись не держала остальные. Пока `Prepare` не скачал и не загрузил модель (при первом запуске — до получаса), очередь не начинает работу.

Готовую расшифровку повторно не запускают (каждый прогон — четыре потока процессора на время записи): в очередь ставится только запись без расшифровки или со сбоем, и только если у неё есть сохранённый звук.

Фильтр галлюцинаций знает только русские фразы (`language: ru`); при автоопределении или английской речи английские хвосты («Thank you for watching») не вырезаются, а сказанное вслух «продолжение следует» вырежется.

Время в заголовке расшифровки — по часам сервера с поясом (в Docker это UTC); в сообщении в чате времени нет.

**Скорость** (оценка по замеру ADR-0041, не замер): на Zen 4 — около 0,4 длительности речи; на i7-6700 — до 1×. Тишина почти бесплатна (VAD), поэтому час встречи с четырьмя участниками ≈ час суммарной речи, а не четыре.

Ни звук, ни текст не пишутся в лог — только статус ответа сервиса.

## 5. Интерфейс

- В канале — список записей: дата, длительность, участники, статус расшифровки.
- Карточка записи: текст расшифровки (показать/скачать `.md`), «Transcribe» для записей без расшифровки и «Try again» после сбоя; дорожки участников — проигрыватель и скачивание по отдельности.
- Синхронное воспроизведение всех дорожек в браузере и общий файл — потом.

## 6. Порядок работ (отдельные PR)

2. Запись запасного пути через WebSocket (WebM).
3. Контейнер whisper, клиент, очередь расшифровки, карточка записи.

## Открытые вопросы

- Записи **временных каналов** (huddle, группы) и **удалённых каналов** недоступны: доступ проверяется по каналу, а временные каналы удаляются через час после звонка. Файлы остаются до срока хранения. Нужно решить: хранить права доступа в самой записи или удалять записи вместе с каналом.

Решено 25.11.2026: включать запись может любой участник, включая гостей; записи видят участники канала.

## Отвергнутые варианты

- **Запись в браузере** (`MediaRecorder` у каждого): зависит от вкладки участника, теряется при закрытии, требует выгрузки файлов.
- **Сведение на лету** в один файл: декодирование, микширование и кодирование на сервере — процессор и зависимость от ffmpeg; для расшифровки всё равно нужны раздельные дорожки.
- **Расшифровка в реальном времени:** Whisper не потоковый, а постоянная нагрузка на 4 потока мешала бы самому SFU.
- **Облачное распознавание:** звук уходит наружу — то же, что отвергнуто в ADR-0041 платформы.
