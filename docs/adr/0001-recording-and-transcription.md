# ADR-0001 — Запись разговоров и расшифровка в текст

- **Статус:** Предложено 25.11.2026
- **Контекст:** по итогам звонка нужна запись голоса и текст «кто что сказал». Распознавание — тем же стеком, что в платформе ([platform ADR-0041](../../../platform/docs/adr/0041-voice-input.md), приложение `platform-apps/apps/whisper`): свой faster-whisper, звук не уходит с сервера.

## Решения в двух словах

| Вопрос | Решение сейчас | Потом |
|---|---|---|
| Где распознаём | отдельный контейнер speaches рядом с Vocala | встроить в платформу (тот же API — меняется только адрес) |
| Кто включает запись | любой участник звонка | права |
| Что пишем | только голос, дорожка на участника, без сведения | общий файл, видео |
| Хранение | локально, 30 дней | S3 (интерфейс закладываем сразу) |
| Кто видит записи | все участники канала | права |

## 1. Запись — на сервере, дорожка на участника

SFU и так получает звук каждого участника отдельным RTP-потоком (`forwardRTP`, `internal/webrtc/sfu.go`). Пока в канале идёт запись, тот же цикл пишет пакеты аудио в Ogg/Opus через `pion/webrtc/v4/pkg/media/oggwriter`:

- **без перекодирования** — копирование пакетов, процессор не тратится;
- **говорящий известен точно** — у каждого свой файл, диаризация не нужна;
- **без ffmpeg** — сведение в один файл не делаем (решение «проще и производительнее»).

Каждый файл — **сегмент**: от появления дорожки участника до её конца. Переподключение, перезаход, ICE restart с новой дорожкой — новый сегмент. Для сегмента храним время начала по часам сервера; по нему расшифровка раскладывается на общую шкалу времени.

Ogg-писатель pion считает время по записанным сэмплам, а не по RTP-меткам, поэтому:

- потерянные пакеты (пропуск короче секунды) заполняются кадрами тишины — иначе файл короче звонка и всё после потери сдвигается;
- пауза дольше секунды или скачок RTP-меток назад (сброс у клиента) — новый сегмент со своим временем начала.

**Путь пересылки звука не ждёт ни диска, ни базы.** SFU копирует пакет в очередь записи (4096 пакетов) и идёт дальше; файлы пишет отдельная горутина на каждую запись. Переполненная очередь теряет пакеты записи, а не задерживает звонок; число потерь пишется в лог.

**Android** (`USE_WS_MEDIA`) шлёт звук не через WebRTC, а кусками WebM по WebSocket (`handleBinaryMedia`, `internal/signaling/hub.go`). Эти куски дописываются в сегмент `.webm` как есть; новый заголовок WebM (переподключение) — новый сегмент. Отдельный PR после основного.

### Включение и выключение

- Кнопка «Запись» у любого участника звонка; остановить может любой.
- Запись останавливается сама, когда из звонка ушёл последний участник, и по пределу длительности (`recording.max_hours`, по умолчанию 4) — чтобы забытая запись не писала сутками.
- Сервер рассылает всем в канале `recording_state`; у всех, включая гостей, — красный индикатор «Идёт запись». Вошедший во время записи видит предупреждение при входе.
- Одна активная запись на канал; запустить новую можно не чаще раза в 2 секунды.
- Остановка сразу сообщается всем, файлы дописываются в фоне. В сообщении об остановке есть `recording_id`: клиент не гасит индикатор новой записи из-за запоздавшей остановки старой.
- Запись без звука (никто не говорил) удаляется при остановке.

## 2. Хранилище — интерфейс с первого дня

```go
// internal/storage
type Blobs interface {
    PutFile(ctx context.Context, key, localPath string) error // переносит готовый файл
    Open(ctx context.Context, key string) (io.ReadCloser, error)
    Delete(ctx context.Context, key string) error
}
```

- Сейчас — `local`: каталог `storage.local.dir`, по умолчанию `storage` рядом с файлом базы (`/var/lib/vocala/storage` в пакетах, том данных в Docker). Ошибка настройки хранилища не мешает серверу стартовать: запись выключается с ошибкой в логе.
- Потом — `s3`: тот же интерфейс, настройки `storage.s3.*`. Код записи и расшифровки об этом не знает.
- Пока идёт запись, сегмент пишется во **временный локальный файл** (в S3 нельзя дописывать потоком). По закрытию сегмента — `Put` в хранилище и удаление временного. Для `local` это переименование.
- В базе — **ключи**, не пути: `recordings/{recording_id}/{segment_id}.ogg`, `recordings/{recording_id}/transcript.md`.

## 3. Данные

```
recordings          id, channel_id, started_by, started_at, ended_at,
                    status (recording|processing|ready|failed), transcript_key
recording_segments  id, recording_id, user_id, display_name, started_at,
                    duration_ms, key, format (ogg|webm)
transcription_jobs  recording_id, status, attempts, error, updated_at
```

`display_name` пишется в сегмент сразу: гостевые сессии временные, через месяц имени гостя уже не найти.

**Срок хранения** — `recording.retention_days: 30`, по образцу `database.chat_retention_days`: фоновая чистка удаляет файлы из хранилища, затем строки. `0` — хранить всегда.

## 4. Расшифровка — после звонка, очередь на одно место

Контейнер speaches с теми же закреплёнными образом (digest как в `platform-apps/apps/whisper/app.yaml`) и настройками: `faster-whisper-medium`, `int8`, CPU, 4 потока, `WHISPER__TTL=-1`, без UI. В `docker-compose.yaml` — сервис `whisper` без опубликованного порта, видит его только `vocala`. В deb-пакет не входит: `transcription.url` пуст — запись работает, расшифровки нет.

Клиент — порт `backend/internal/speech` из платформы (`Prepare` готовит модель при старте, `Clean` вырезает «Продолжение следует», «Субтитры сделал…» и т. п.).

Порядок:

1. Запись остановлена → `status=processing`, задача в `transcription_jobs` (в базе — переживает перезапуск).
2. Один фоновый обработчик на сервер, сегменты по одному: `POST /v1/audio/transcriptions` с `language=ru`, `response_format=verbose_json`, `timestamp_granularities[]=segment`, `vad_filter=true`.
3. Фразы из ответа (`segments[].start/end`, секунды) сдвигаются на начало сегмента, всё сортируется по времени и склеивается в `transcript.md`:
   ```
   [00:01:23] Иван: …
   [00:01:31] Мария: …
   ```
4. `transcript.md` → хранилище, `status=ready`, в чат канала — сообщение со ссылкой.

Проверено по исходникам speaches 0.8.3 (`routers/stt.py`, `api_types.py`, `config.py`): `verbose_json` возвращает сегменты со `start`/`end`; `timestamp_granularities[]` принимается; `vad_filter` по умолчанию включён; ogg/webm декодирует PyAV. Ограничения размера в коде нет — час opus (≈15 МБ) уходит одним запросом.

**Тайм-аут** — не фиксированные 3 минуты, как в платформе, а от длины сегмента: `5 мин + 2 × длительность`. Ошибка — до 3 попыток, затем `status=failed` и кнопка «Повторить».

**Скорость** (оценка по замеру ADR-0041, не замер): на Zen 4 — около 0,4 длительности речи; на i7-6700 — до 1×. Тишина почти бесплатна (VAD), поэтому час встречи с четырьмя участниками ≈ час суммарной речи, а не четыре.

Ни звук, ни текст не пишутся в лог — только статус ответа сервиса.

## 5. Интерфейс

- В канале — список записей: дата, длительность, участники, статус расшифровки.
- Карточка записи: текст расшифровки, скачать `.md`; дорожки участников — проигрыватель и скачивание по отдельности.
- Синхронное воспроизведение всех дорожек в браузере и общий файл — потом.

## Открытые вопросы

- Записи **временных каналов** (huddle, группы) и **удалённых каналов** недоступны: доступ проверяется по каналу, а временные каналы удаляются через час после звонка. Файлы остаются до срока хранения. Нужно решить: хранить права доступа в самой записи или удалять записи вместе с каналом.

Решено 25.11.2026: включать запись может любой участник, включая гостей; записи видят участники канала.

## Отвергнутые варианты

- **Запись в браузере** (`MediaRecorder` у каждого): зависит от вкладки участника, теряется при закрытии, требует выгрузки файлов.
- **Сведение на лету** в один файл: декодирование, микширование и кодирование на сервере — процессор и зависимость от ffmpeg; для расшифровки всё равно нужны раздельные дорожки.
- **Расшифровка в реальном времени:** Whisper не потоковый, а постоянная нагрузка на 4 потока мешала бы самому SFU.
- **Облачное распознавание:** звук уходит наружу — то же, что отвергнуто в ADR-0041 платформы.
